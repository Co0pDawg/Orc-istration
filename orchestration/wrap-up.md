# Wrap-up

How the orchestrator finishes an orchestrated task: full test projects once, the diff read, the pre-PR review tier, the cost log, the handoff note, the board marked Done. Use it when the builder/refuter loop of an orchestrated task is accepted and before reporting it done or opening the PR; not in sprint mode, which waives most of this. The rulebook's "Build loop", "Pre-PR review tiers" and "Cost log" sections win over anything here. The generated `wrap-up` skill points here.

`<setup>` is the setup checkout (CHECKOUT in the generated skill). Find the Orc-istration checkout: the "Setup checkout (this machine)" line in the rulebook's tool notes, else `setupCheckout` in `config.json` (under `ORC_DATA_DIR` when set, else under `~/.orc/`), else ask the user. Call it CHECKOUT and confirm `CHECKOUT/orchestration/wrap-up.md` exists there; if it does not, stop and say so. Commands run as `node "<setup>/tools/orc.mjs" ...`, quoted.

Show this as a visible checklist and tick each step as it finishes.

1. **Full tests.** Run each full test project once, by project name, one at a time, in the background. Run them while a refuter does its static pass if one is still running. A green run older than the last edit does not count.
2. **Diff read.** Read the whole final diff yourself against the base branch. Confirm any defect an agent reported by reading the code or reproducing it, and say which.
3. **Review tier.** Run `review-tier --base origin/<base>` in the repo.
   - **Light** only when all three hold: the diff is tests and docs only; the refuter gave ACCEPT after mutation checks; the refuter's brief used the repo's test conventions as its checklist. Then run a docs and comment review only.
   - **Full** otherwise: run the review panel (`<setup>/review/PROCEDURE.md`, staged 3+3; the tool notes say which command or skill runs it).
   - Escalate Light to Full if it finds anything beyond doc wording. Fix nits inline only when cheap and in a file already in the diff; log the rest `not-actioned`.
   - **Second reviewer (Full):** read `routing.refuter` from `config.json` (under `ORC_DATA_DIR` when set, else `~/.orc/`). If `config.json` exists but cannot be read or parsed, tell the user and record that in the skip line, the review run log (below) and the PR description — never report it as "no second reviewer". Otherwise, treat a plain tool-id string as a one-item list and pick its first entry that differs from every tool that ran a refuter in this task — or, when no refuter ran, from the orchestrator's own tool (`fallback` alone is not used). With none (no config, no `routing.refuter`, or no differing tool), say in one line that no second reviewer tool is configured, record the skip in the review run log (below), and skip. Otherwise, before the second review commit all of the task's changes, the review panel's fixes included, on the feature branch, and record that commit. If a task file is still uncommitted, or `git diff origin/<base>...HEAD` is empty, do not run it: tell the user and record in the review run log (below) and the PR description that it did not run, and why. Write a marching-orders brief from `node "<setup>/tools/orc.mjs" brief new --role refuter` outside the reviewed repo (the tool's scratch folder, or the system temp folder when it has none) covering `git diff origin/<base>...HEAD` and naming that commit, filling all 11 items so `node "<setup>/tools/orc.mjs" brief lint <file> --role refuter` passes (verification commands in item 4, an output cap in item 6, the task's acceptance criteria verbatim — or `none: <why>` — plus any approved plan decisions and mockup references the loop's refuter was given as intent in item 9, data precondition in item 10, and `BOARD: none` in item 11). Tell the second reviewer in the brief that any check its sandbox refuses (for example `EPERM` or `EACCES`) is `NOT RUN`, not a defect, and, where the tool notes say temp-folder renames are refused, to point `TEMP` and `TMP` at a folder under `.orc/tmp/`. Run the **Clean-tree check** from `<setup>/review/PROCEDURE.md` ("Routed agents") before and after the dispatch, and neither edit nor commit in the checkout until the after-check has run. Dispatch once from the repo root, in the background where the tool can, saving stdout only to a file outside the reviewed repo (the tool's scratch folder, or the system temp folder when it has none) and stderr to a separate file there: `node "<setup>/tools/orc.mjs" dispatch --tool <tool> --role refuter --brief <file> --timeout 1800`. `orc dispatch` prints `command:` and `stdin:` lines to stdout before streaming the tool's output, so skip those leading lines when reading the saved file; for a tool such as Antigravity that prints a JSON result object, take that object from the output (the last JSON object starting a line with a string `status`, as `dispatch` itself reads it) and use its `response` string before checking the verdict. A verdict counts only when the final report has a line `VERDICT: ACCEPT` or `VERDICT: REWORK` with exactly one of the two words; a line holding both is the unfilled template and means no verdict. `--tool` never falls back: if the run cannot start (including a spent usage limit), exits non-zero, or returns no verdict, tell the user and record in the review run log (below) and the PR description that the second review did not run, and why — never substitute the same tool. When it does run, rerun anything it listed as `NOT RUN` yourself, and record the tool, the reviewed commit and its verdict in the review run log (below) and the PR description. **Run-log record:** in every case above (verdict, failure or skip), append a `## Second review` section to the latest of this branch's review run logs with plain lines. This branch's logs are the files in `.orc/reviews/` (or the repo's configured run-log folder; `review/calibration.md`) named exactly `<YYYY-MM-DD>-<branch-slug>.md` or `<YYYY-MM-DD>-<branch-slug>-<n>.md`, with `n` a number, whose `# Review Log:` header does not name another branch; the latest has the newest date, then the highest `n`. They record the tool (or `none`), the reviewed commit (or `HEAD`), and the verdict or why it did not run, so a later `draft-pr` session can read it (the calibration parser ignores this section; do not put a finding table or `Leads:`/`Verification:` lines in it). Handle a `REWORK` verdict like any refuter's: the second review runs once, so after a `REWORK` fix the re-check is the loop's normal fresh refuter, and the second tool runs again only if the user asks.
4. **Docs co-change.** If the repo has a rule that user-facing changes update its README or wiki in the same change, check that they did.
5. **Cost log.** Draft it with `costlog --session <session id>`:
   - Local board: add `--board <address> --board-repo <board repo>`.
   - Artifact board: read the session doc and every card whose `session` is this one, write them to `<scratchpad>/board-export.json` as `{"sessions": {"<session id>": {...}}, "cards": {"<card id>": {...}}}` with bare ids as keys (`t1`, not `cards/t1`, so they match each event's `card`), and pass `--board-export` with that file.
   Fill each `TODO` and save it as `~/.orc/log/<date>-<project>-<slug>.md` (`ORC_DATA_DIR` when set), following `<setup>/orchestration/log/TEMPLATE.md`. The orchestrator's context size comes from where the tool notes' "Cost log" line says. Target: orchestrator share under 20% of tokens.
6. **Anomalies.** For anything odd in this task that no rule covers, add one line to `~/.orc/log/anomalies.md` beside the cost logs. Search the file for the same cause first and promote a repeat (`<setup>/orchestration/README.md`, "Anomaly log"). Skip the step when there was nothing.
7. **Handoff.** Update the task's handoff doc with the decisions, what is done, what is open and the exact next step.
8. **PR.** Commit only what remains on the feature branch, never on `main` or `develop`. Open a draft PR against the base branch, with the PR footer the tool notes give. Confirm before pushing.
9. **Board.** Write the commit and PR fields, then mark the session Done with `completed` and a closing `now` (see `orchestration/board.md`).
