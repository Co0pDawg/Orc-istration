# Command reference

The long reference for `node tools/orc.mjs`. `node tools/orc.mjs help` lists every command, and `node tools/orc.mjs help <command>` lists its options. The commands that read this checkout (`build`, `check`, `sync`, `golden`, `install`, `uninstall`, `status`, `brief`, `dispatch` and `hooks`) take `--repo <dir>` (default: the checkout running orc.mjs), and only their help lists it; for `standards` it names the project instead.

## Regenerating the goldens

`golden [--tool <id>|all]` (default `all`) regenerates `tests/golden/<tool>/` from the same build the golden test compares against: `models.json` only (no `models.local.json`), no profiles and no board line. It prints `wrote`, `unchanged` or `deleted` per file, deletes any file under `tests/golden/<tool>/` the build no longer produces, and writes nothing outside `tests/golden/`. When the build has errors it prints them, writes nothing and exits 1. Review the result with `git diff tests/golden`.

## Build, install, uninstall and status

`build` prints each tool's full gap list and appends it to that tool's rulebook:

```
node tools/orc.mjs build --tool all              # writes dist/<tool>/... (untracked)
node tools/orc.mjs install --tool antigravity    # dry run: prints create / replace / unchanged per file
```

`--apply` writes; a replaced file is first copied to `<file>.orc-backup-<stamp>`. `install` refuses `--tool claude-code` without `--home`, because this repo is designed to be checked out as `~/.claude`. `--board` and `--board-repo` add this machine's board address to the installed rulebook. An artifact address (`https://claude.ai/artifact/...` or `claude.ai/code/artifact/...`) is for `--tool claude-code` only and needs no `--board-repo`: its line says to write it with ArtifactData, as the tool notes say. Other tools refuse it. Installing both Antigravity and Gemini CLI puts two rulebooks in `~/.gemini`; `install` warns and names the file to remove.

**Manifest.** `install --apply` records every file it wrote, with the sha256 of the bytes, in `<home>/<tool folder>/.orc-manifest.<tool>.json` (for example `~/.gemini/.orc-manifest.antigravity.json`, so Antigravity and Gemini CLI keep separate manifests in the shared folder). It is written last, only when the install succeeded. On re-install a file still matching its recorded hash is replaced without `--force`, so role edits need no `--force`. A file edited by hand since install (`REPLACE EDITED`), or a differing file not in the manifest and without the generated-by marker (`REPLACE HAND-WRITTEN`), refuses the whole install unless `--force` is given (with a backup). A file whose role was removed is deleted when untouched and kept (and reported) when edited; the dry run lists both. A corrupt or foreign manifest, or one naming a path outside the tool folder, is refused and nothing is deleted. Before any write, backup or delete, every target's real path must stay inside the tool folder, and a symlink or junction below the tool folder refuses the whole install or uninstall; so does a manifest entry that is not a regular file.

`uninstall --tool <id> [--home <dir>] [--apply] [--force]` is a dry run by default. It deletes exactly the manifest's files that still match their hash, keeps edited ones (`--force` deletes them after a backup), removes the empty folders install created, and touches nothing else. When it keeps a file, the manifest stays and lists exactly the kept files, so `uninstall --apply --force` can remove them later; otherwise the manifest is removed. Without a manifest it refuses; remove the files by hand. `--tool claude-code` needs `--home`.

`status --tool <id> [--home <dir>]` compares an installed copy with what would be generated now, without writing: each file is `same`, `differs (first difference at line N)`, `edited since install, differs (...)`, `missing`, `stale (role removed)` or `extra` (a file in the agents folder that no role generates, marked `not installed by orc` when a manifest exists; install backups are skipped). It exits 0 only when everything is `same`.

Every `install` ends with a pointer to the per-project coding-standards setup, naming the absolute path of this checkout's `orchestration/standards.md`: `Next: ...` after `--apply`, `After --apply, next: ...` on a dry run. `install` (and its dry run) also adds one line to the installed rulebook's tool notes, after any Board line: `Setup checkout (this machine): <abs path>. Standards setup: node "<abs path>/tools/orc.mjs" standards ...; procedure: <abs path>/orchestration/standards.md.`, where `<abs path>` is the checkout running orc.mjs, with forward slashes. It is derived, not recorded in the manifest; `status` adds the same line, and `build`, `check`, `sync` and `golden` never do.

`install --apply` records its `--profile`, `--board` and `--board-repo` values in the manifest (`options`). A later `install` or `status` without those flags reuses them and says so in one line; a flag given replaces the recorded value for that option, and `--no-profile` / `--no-board` clear it.

`build`, `install` and `status` take `--profile <name>` (repeatable or comma-separated) to append `profiles/<name>.md` after the tool notes; `check` and `sync` reject `--profile`, and the goldens use no profile. The rulebook core is the compact, generic `AGENTS.md`; `dotnet-azure-devops` is too large for Antigravity's 24,000-byte cap (the build fails with the size message), so use it with uncapped tools or as a project-level rules file.

## Method tooling

These commands check or do the manual steps the rulebook asks for. None of them writes to the board.

- `brief new [--role <name>] [--out <file>]` (with `--out`, as for `costlog`, an existing file is refused unless `--force` is given) prints the marching-orders template, parsed from the numbered list under "Marching orders" in `AGENTS.md` (items 9 to 11 only for builder, refuter and debugger; item 9, Intent, is prefilled `n/a` for a builder or debugger). `brief lint <file> [--role <name>]` checks a brief: every item present, in order and filled in; nothing but an optional title heading before item 1 and nothing but the `BOARD:` line after the items' own (indented or fenced) lines; item 4 names a command (a code span, a fence, or a line starting with a runner word such as `npm` or `node` and an argument); item 6 states a cap; for `--role refuter`, item 9 (Intent) is a path, the criteria or `none: <why>`, never empty, `n/a`, a placeholder such as `TBD`, or a `none` without the colon form; a brief still on the old numbering is told that Intent is new at item 9; `BOARD: none` is accepted; a `BOARD:` line has the form `BOARD: <address> card cards/<id> stage <label>` (Claude Code's `slug <uuid>` after the address is accepted). It exits 1 with one line per problem.
- `review-tier [--base <ref>] [--repo-dir <dir>]` reads `git diff --name-only --no-renames <base>...HEAD` (default base `origin/main`) and prints `Light-eligible` when every path is a test (`tests/`, `test/`, `__tests__/`, `spec/`, `*.test.*`, `*.spec.*`, `*_test.*`) or a doc (`*.md`, `docs/`), else `Full` with the first three deciding paths. Light still needs a refuter ACCEPT after mutation checks (conditions 2 and 3 of "Pre-PR review tiers"). Prompts count as product, not docs: `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `SKILL.md`, `*.agent.md`, `roles/`, `agents/`, `profiles/`, `.claude/`, `.agents/`, `.codex/`, `.cursor/`, `.gemini/`, `adapters/*.notes.md`, `standards/`, `orchestration/standards.md` and `orchestration/sprint.md` make it `Full`; uncommitted changes print a warning, since they are not in `<base>...HEAD`.
- `costlog --session <id> (--board-export <file> | --board <http://localhost:port> --board-repo <dir>) [--out <file>]` drafts a cost log in the "Record format" of `orchestration/README.md`: one row per `<agent> dispatched on #<task>` event, ended by the next top-level event naming the same card (its text is the Result). Card `tokens` go in a per-card table, because the board records tokens per card, not per dispatch. Model, tools, value, project, orchestrator context, loop signal and spec misses are `TODO`. `--board` reads through `node <board-repo>/local/board.js export`.
- `dispatch --tool <id> --role <name> --brief <file> [--dry-run] [--timeout <seconds>] [--no-lint]` runs one role headlessly at its tier: Antigravity as `agy -p <brief> --agent <role> --model <models.json headless slug> --output-format json` (agy reads stdin only in stream-json mode, so the brief is one argument), Claude Code as `claude -p --agent <role> --model <tier model>` with the brief on stdin. Other tools exit 1 with "no headless recipe". The brief is linted first, is never put through a shell, `--dry-run` prints the command and exits 0, a real run streams the tool's output and exits with its code, and `--timeout` (whole seconds, 1 to 86,400) kills the process tree (exit 124); Ctrl-C or a kill of orc kills the tree too (exit 130 or 143). The brief is read once, BOM-stripped and UTF-16 decoded, and that text goes to the tool. `ORC_TOOL_BIN_<TOOL>` (e.g. `ORC_TOOL_BIN_CLAUDE_CODE`) points at the executable; a Windows `.cmd` shim is not started. A brief passed as an argument is refused (nothing started) when it holds a NUL byte or the command line would pass about 32,000 bytes; a tool that is not installed is named with its override variable.
- `hooks --home <dir> [--apply] [--node]` merges only the `hooks` block of `settings.example.json` (or, with `--node`, of `hooks.node.example.json`: the board reminder as `node <home>/.claude/tools/board-reminder.mjs`, no PowerShell) into `<home>/.claude/settings.json`, creating it when absent. `<you>` paths become the real home. A hook is added only when no hook under that event and matcher runs the identical command; the same command under a different matcher is added beside it, with a note naming the existing matcher; existing keys and hooks are never removed, reordered or rewritten. It is a dry run without `--apply`; `--apply` backs the file up first (only once the new content could be written), keeps a UTF-8 BOM, and refuses a file whose top level is not a JSON object. `--home` has no default.
- `calibration [--logs <dir>] [--min-precision <0..1>] [--out <file>] [--force]` reads the review panel's run logs (default `<repo top>/.orc/reviews`, from the current folder) and prints per-lane precision from their verdicts; lanes under `--min-precision` are flagged. Format and procedure: `review/calibration.md`.
- `metrics capture --workflow <name> [--session <id> | --transcript <path>] [--log <run log>] [--mode lite|full] [--version <v>] [--out <dir>] [--print]` writes one run's token, context and outcome metrics from a Claude Code transcript (default `<repo top>/.orc/metrics/`); `metrics report [--dir <dir>] [--prices <file>] [--out <file>] [--force]` aggregates them. Format: `review/metrics.md`. Neither reads `--repo`.
- `check` also validates every archive entry in `standards/` (except `README.md`): `id` equals the file name, `kind` is `language`, `framework` or `tool`, `detect` is a non-empty list, every `requires` id exists, `reviewed` is `YYYY-MM-DD`, `sources` is non-empty and every `[n]` in the body (outside code) is within range, and the body has a `## Review checklist` section with at least one `- [ ]` item.
- `check` also validates `models.json` and `models.local.json`: tool ids must be adapters, tiers `low`, `mid`, `high` (plus `headless` slugs per tier), values strings, and `effort` one of `low`, `medium`, `high`, `xhigh`, `max`, `ultra`.

CI (`.github/workflows/test.yml`) runs `npm test` and `check` on Ubuntu and Windows, and the worklog self-test on Windows.

## Repo standards

`standards` reads the archive in this checkout's `standards/` (format in `standards/README.md`). For this command `--repo <dir>` names the project, not the Orc-istration checkout. `--stack`, `--from` and `--json` are refused by every other command. Within `standards`, `list` and `show` take no option but `--repo`; `detect` refuses `--stack`, `--from`, `--out`, `--force` and `--apply`; `apply` refuses `--json`. The setup procedure that uses it is `orchestration/standards.md`.

- `standards list` prints one line per archive entry: `<id>  <kind>  <title>  (reviewed <date>)`.
- `standards show <id>` prints the archive file. An unknown id exits 1 and lists the known ids.
- `standards detect [--repo <dir>] [--json]` (default: the current folder) walks the project without following symlinks or junctions, skips folders named `.git`, `node_modules`, `bin`, `obj`, `dist`, `build`, `vendor`, `target`, `.venv`, `venv`, `__pycache__` and `.claude`, and stops after 50,000 entries with a warning. A folder it cannot read is skipped and counted, with `WARN could not read N folder(s); results are partial` on stderr; an unreadable project root exits 1. It matches each entry's `detect` globs (`*` and `?`, case-insensitive) against file base names and prints, per detected id, the match count and up to 3 example paths, most matches first; ids pulled in only through `requires` (transitively) show `required by <id>`. `--json` prints `{repo, standardsFile, current, detected: [{id, title, kind, matches, examples, requiredBy}], archive, truncated, unreadable}`, where `standardsFile` says whether `STANDARDS.md` exists and `current` is `{stacks, imports}` parsed from its orc marker, or `null` when it has no valid marker. It exits 0 even when nothing is detected.
- `standards apply --repo <dir> (--stack <ids> | --from <path>)... [--out <rel>] [--apply] [--force]` composes the project's standards file:
  - `--stack` takes archive ids (repeatable or comma-separated) and adds their `requires`, saying so. `--from` (repeatable) takes a `.md` file, or a folder whose `.md` files are taken non-recursively, sorted by name; a folder leaves out the target, and a `--from` that is the target (same real path) exits 1. A `--from` file whose frontmatter has a top-level `sources:` key is an archive-format entry: it must parse (`#` comment lines are ignored), its `sources` must be a non-empty list and it must have an `id`, or it exits 1 with `--from <path>: <file name>: <parse error | sources must be a non-empty list | an archive-format entry needs an id>`; it is then validated with `check`'s per-entry rules (except that `requires` ids need not exist), and an invalid one exits 1 with its problems. Frontmatter without `sources:` (such as `id:` and `title:` only) is a plain import. The marker records imports by file name, so one file reached twice (repeated, a folder plus a file in it, or the same file in another case on Windows) exits 1 with `passed twice: <path>`, and two different files with the same file name ignoring case (two folders each with `style.md`), or a file name containing `,`, `;` or `-->`, exit 1 naming the files. `--out` defaults to `STANDARDS.md` and must be relative, stay inside the project, have no `.git` segment, and not pass through an existing file. Builders, refuters and `detect` read the root `STANDARDS.md`, so a non-default `--out` is for review or staging.
  - Sections: languages, then frameworks, then tools (each by id), then archive-format imports, then the other imports, each group in the order given. Each stack section is the archive body with every heading demoted one level, a `Sources` list numbered to match its `[n]` citations, and a `Reviewed <date>` line. An archive-format import is rendered like a stack section and recorded in the marker's `imports` by file name. Each other import is `## Imported: <file name>` and the file's body, with any leading YAML frontmatter removed and headings demoted outside fenced code. A leading `---` ... `---` pair is frontmatter when it has a top-level `key:` line and every other non-blank line is a `#` comment, an indented line, or a top-level `- ` item under a key; otherwise (a heading over a list, say) it is a pair of horizontal rules and is kept. A pair around a lone `Note: x` line is valid YAML, so it is stripped.
  - Line 1 is `<!-- orc standards: stacks=<ids>; imports=<names>; sha256=<hex> -->`; the hash covers the rest of the file (LF line endings), so a later run can tell an untouched file from an edited one.
  - Without `--apply` it is a dry run: it prints the target, its state and the section list, and writes nothing. States: `create` (absent), `unchanged` (identical), `replace` (marker present, hash matches, nothing dropped), `REPLACE DROPS` (hash matches, but the new composition leaves out a stack id or import name the marker records; the refusal names them), `REPLACE EDITED` (hash does not match) and `REPLACE HAND-WRITTEN` (no marker). With `--apply`, the last three are refused with exit 1 unless `--force` is given, which first copies the file to `<file>.orc-backup-<stamp>`. As with `install`, the dry run still exits 0 for them and adds an `--apply would refuse` line.
  - It refuses a target whose path, or any folder below the project, is a symlink or junction, or whose real path leaves the project. An unknown stack, a missing `--from` path, or neither `--stack` nor `--from` exits 1. It writes only the `--out` file (through a temp file in the same folder, renamed over the target), as UTF-8 with LF line endings, and never fetches anything: save a URL as Markdown first and pass it with `--from`.
