# Command reference

The long reference for `node tools/orc.mjs`. `node tools/orc.mjs help` lists every command, and `node tools/orc.mjs help <command>` lists its options. The commands that read this checkout (`build`, `check`, `sync`, `golden`, `install`, `uninstall`, `status`, `brief`, `dispatch`, `doctor`, `hooks`, `corpus`, `bench` and `queue`) take `--repo <dir>` (default: the checkout running orc.mjs), and only their help lists it; for `standards` it names the project instead.

## Regenerating the goldens

`golden [--tool <id>|all]` (default `all`) regenerates `tests/golden/<tool>/` from the same build the golden test compares against: `models.json` only (no `models.local.json`), no profiles and no board line. It prints `wrote`, `unchanged` or `deleted` per file, deletes any file under `tests/golden/<tool>/` the build no longer produces, and writes nothing outside `tests/golden/`. When the build has errors it prints them, writes nothing and exits 1. Review the result with `git diff tests/golden`.

## Build, install, uninstall and status

`build` prints each tool's full gap list and appends it to that tool's rulebook:

```
node tools/orc.mjs build --tool all              # writes dist/<tool>/... (untracked)
node tools/orc.mjs install --tool antigravity    # dry run: prints create / replace / unchanged per file
```

`--apply` writes; a replaced file is first copied to `<file>.orc-backup-<stamp>`. This repo is a standalone checkout that installs into each tool's home folder, so `--home` defaults to your home for every tool, including `claude-code`. `--board` and `--board-repo` add this machine's board address to the installed rulebook (defaulting from `~/.orc/config.json` `board` when neither flags nor the manifest set or clear one). An artifact address (`https://claude.ai/artifact/...` or `claude.ai/code/artifact/...`) is for `--tool claude-code` only and needs no `--board-repo`: its line says to write it with ArtifactData, as the tool notes say. Other tools refuse an artifact `--board` flag; when an artifact address comes from `config.json` `board.url`, non-Claude tools get no Board line and one notice saying so. Installing both Antigravity and Gemini CLI puts two rulebooks in `~/.gemini`; `install` warns and names an orc-generated file to remove, and also warns when the other file exists and is hand-written (without asking to remove it). For `--tool claude-code`, `install` (and `sync`) writes the rulebook (`CLAUDE.md` and `AGENTS.md`), the roster and review-panel `agents/*.md`, the three generated review commands and the six workflow commands (`adapters/claude-code/commands/*.md`) to `<home>/.claude/commands/`, the `orc-permissions` skill (`adapters/claude-code/skills/orc-permissions/SKILL.md`) to `<home>/.claude/skills/orc-permissions/SKILL.md`, and the four hook scripts (`tools/guard.ps1`, `tools/guard.mjs`, `tools/board-reminder.ps1`, `tools/board-reminder.mjs`) to `<home>/.claude/tools/`, all recorded in the manifest and compared by `status` like the generated files; a differing hand-copied hook script, command or skill with no manifest entry is kept and reported as `kept (hand-copied <kind> ...)` rather than refusing the install, and `--force` replaces it with a backup. The remaining tool-neutral skills (`skills/{board,brief,repo-standards,sprint,wrap-up}`) are still copied by hand until skill generation lands.

**Manifest.** `install --apply` records every file it wrote, with the sha256 of the bytes, in `<home>/<tool folder>/.orc-manifest.<tool>.json` (for example `~/.gemini/.orc-manifest.antigravity.json`, so Antigravity and Gemini CLI keep separate manifests in the shared folder). It is written last, when the install succeeded; when a write fails part way it is still written, recording every file written so far, and the install stops with `install stopped: ... records what was written, so uninstall --apply undoes it`. When the manifest itself cannot be written, the install fails with `the files were written but not recorded: cannot write <manifest> ...`. On re-install a file still matching its recorded hash is replaced without `--force`, so role edits need no `--force`. A file already in place, identical to the generated one and in no manifest (such as an agent file or hook script copied by hand), stays the owner's: the install prints `unchanged: <path> (already there and in no orc manifest: not recorded, uninstall leaves it)`, does not record it, and `uninstall` leaves it. A copy left from an old `~/.claude` checkout is such a file; to hand it over to `orc`, delete it first and then run `install --apply`. A file an earlier install recorded keeps its entry. The same rule applies to orc's own files when the manifest is gone (deleted by hand, or a process killed before it wrote one): a re-install records none of the files already in place, so `uninstall` leaves them, and they are deleted by hand. A file edited by hand since install (`REPLACE EDITED`), or a differing file not in the manifest and without the generated-by marker (`REPLACE HAND-WRITTEN`), refuses the whole install unless `--force` is given (with a backup); `--force` replaces every hand-written or hand-copied file with a backup and records it in the manifest, so a later `uninstall` removes it. A file whose role was removed is deleted when untouched and kept (and reported) when edited; the dry run lists both. A corrupt or foreign manifest, or one naming a path outside the tool folder, is refused and nothing is deleted. Before any write, backup or delete, every target's real path must stay inside the tool folder, and a symlink or junction below the tool folder refuses the whole install or uninstall; so does a manifest entry that is not a regular file.

`uninstall --tool <id> [--home <dir>] [--apply] [--force]` is a dry run by default. It deletes exactly the manifest's files that still match their hash, keeps edited ones (`--force` deletes them after a backup), removes the empty folders install created, and touches nothing else; for a sprint kit it also removes the kit's `settings.json` entries and restores the files the kit replaced (see **Sprint kit** below). When it keeps a file, the manifest stays and lists exactly the kept files, so `uninstall --apply --force` can remove them later; otherwise the manifest is removed. When the manifest records no files (every file was already in place at install), it prints `nothing recorded to delete: files that were already in place at install are not in the manifest; delete them by hand if they are orc's`, deletes nothing and, with `--apply`, still removes the manifest. Without a manifest it refuses; remove the files by hand.

`status --tool <id> [--home <dir>]` compares an installed copy with what would be generated now, without writing: each file is `same`, `differs (first difference at line N)` (for a hand-copied hook script, command or skill with no manifest entry, which a plain `install --apply` keeps, the line adds that `install --apply --force` replaces it), `edited since install, differs (...)`, `missing`, `stale (role removed)` or `extra` (a file in the agents folder that no role generates, marked `not installed by orc` when a manifest exists; install backups are skipped). It exits 0 only when everything is `same`.

Every `install` ends with a pointer to the per-project coding-standards setup, naming the absolute path of this checkout's `orchestration/standards.md`: `Next: ...` after `--apply`, `After --apply, next: ...` on a dry run. A sprint kit install ends instead with the pointer to start a fresh Claude Code session, check that `/sprint` and the roster agents are listed, and follow `docs/interview-machine.md`. `install` (and its dry run, plus `sync`) also adds one line to the installed rulebook's tool notes, after any Board line: `Setup checkout (this machine): <abs path>. Standards setup: node "<abs path>/tools/orc.mjs" standards ...; procedure: <abs path>/orchestration/standards.md.`, where `<abs path>` is the checkout running orc.mjs, with forward slashes. It is derived, not recorded in the manifest; `status` adds the same line, and `build`, `check` and `golden` never do.

`install --apply` records its `--profile`, `--board` and `--board-repo` values (and, for a sprint kit, `sprintKit` and `stacks`) in the manifest (`options`). A later `install` or `status` without those flags reuses them and says so in one line; a flag given replaces the recorded value for that option, and `--no-profile` / `--no-board` clear it. `install --apply --no-board` also records the clear (`noBoard: true`), so a later `install`, `status` or `sync` does not add the `config.json` board back; a later `--board` drops the mark.

**Sprint kit.** `install --tool claude-code --sprint-kit [--stack dotnet|node|python] [--home <dir>] [--apply]` is the install for a borrowed machine ([`interview-machine.md`](interview-machine.md)). It installs the rulebook, roster agents and generated review commands plus `skills/sprint/SKILL.md` as `<home>/.claude/skills/sprint/SKILL.md`, all recorded in the manifest; of the hook scripts it copies only `tools/guard.mjs` (and omits the six workflow commands and `orc-permissions`). A file already in place, identical to the kit's copy and in no manifest (such as a hand-copied `SKILL.md` or `guard.mjs`), is the owner's: it is reported `unchanged (already there and in no orc manifest ...)`, not recorded, and `uninstall` leaves it. A differing hand-copied `guard.mjs` is kept and reported `would keep (hand-copied hook script, differs ...)`, so `status` says `differs` for it and that `install --apply --force` replaces it; `--force` replaces it with a backup. It merges into `<home>/.claude/settings.json` the Node guard hook (the PreToolUse group of `adapters/claude-code/hooks.node.example.json`) and a permission preset. The guard hook is skipped, and not recorded, only when a working guard is already wired: a PreToolUse hook whose matcher fires on both Bash and PowerShell (none, `''`, `*`, or a pattern naming both) and whose command runs the guard as its script (`node [options] <path>/tools/guard.mjs`, or `pwsh`/`powershell ... -File <path>/tools/guard.ps1`, the program bare or by path, and nothing after the script, since a redirect or pipe could discard the denial the guard prints; not after `-e`, `-c`, `-Command` or the like, not behind `echo` or a shell operator), with that script on disk (or about to be written by this install, for `<home>/.claude/tools/guard.mjs`). A guard invocation whose script is gone is reported with a `WARN ... which is not on disk, so it guards nothing` line and left in place, and the kit adds its own guard. The preset goes in `permissions.allow`, each rule as a `Bash(...)` rule and a `PowerShell(...)` twin (the permissions doc: PowerShell rules "use the same shape as Bash rules", and a trailing ` *` "also matches the bare command"): `dotnet build *`, `dotnet test *`, `dotnet run *` and `dotnet restore`; `npm test *`, `npm run *`, `npm start *`, `npm install` and `npm ci`; `pytest *`, `python -m pytest *` and `python -m unittest *`. Restore commands are exact (`npm install`, not `npm install *`, which would also match `npm install -g`). There are no git rules (Claude Code already runs read-only git without a prompt, so a `git log *` rule would only add forms that write, such as `git log --output=<file>`) and no pip rule (outside a virtual environment `pip install -r requirements.txt` installs into the global Python). The wildcard rules run project code by design, and their flags reach further: for example `npm run <script> --script-shell=<program>` runs any program as the script shell, `dotnet build -logger:<assembly>` and `dotnet test --logger`/`--test-adapter-path` load any assembly, and `-o`, `--results-directory`, `--junitxml` or `--basetemp` (which pytest empties) point output at any folder. `--stack` is repeatable or comma-separated; without it the stacks are detected in the current folder (`*.sln`, `*.slnx` or `*.csproj` = dotnet, `package.json` = node, `pyproject.toml` or `requirements.txt` = python), never in this checkout, and none found means no preset. A home whose manifest records a full install (no `options.sprintKit`) refuses `--sprint-kit`, dry run included, with nothing written: the kit would delete that install's hook scripts while its `settings.json` still runs them. The reverse is safe: a plain `install` over a kit reuses the recorded kit. The kit adds no board: `--board` and `--board-repo` are refused and no board warning is printed. Its rulebook gets two lines where the Board line would go: `**Board:** none on this machine (sprint kit) ...`, and a `**Sprint kit:**` line saying only the Node guard (`tools/guard.mjs`) is wired, there is no board-reminder hook, no subagent model or effort is set (so always name `subagent_type`), and nothing is pushed unless the user says so. A plain install's rulebook is unchanged. `settings.json` is merged, never replaced: an entry is added only when missing, an invalid file (not JSON, a non-object `permissions` or `hooks`, or a non-array `permissions.allow`) refuses the whole install before anything is written, and a backup `settings.json.orc-backup-<stamp>` is made once, before the kit's first change. A hand-written file in the way (such as the owner's `CLAUDE.md`) is replaced after a backup without `--force`; a file edited since an earlier install is still refused. The manifest's `kit` record lists exactly the `settings.json` entries and containers the kit added, each replaced owner file's first backup (`restore`) and each backup a re-install made of a kit file (`copies`), and a re-install keeps them. When a kit install stops part way (a write fails), the manifest is still written with every file written so far and every restore entry, and the settings record only if `settings.json` was written, so `uninstall --apply` undoes it. A later `install` or `status` without the flag reuses the recorded kit and stacks; `status` also reports `missing in settings.json: ...` for a missing working guard, a missing rule of the recorded stacks or any allow rule the kit ever added, and `missing in settings.json: unreadable (...)` for a file it cannot read. `uninstall` (no flag needed) first undoes the kit's `settings.json` changes, so a failed write leaves the home and the manifest as they were: it removes only the recorded entries and the empty containers the kit created; when nothing else changed, the original backup goes back byte for byte; when the owner changed the file since, their changes stay and the backup is kept; a file the kit created is deleted once empty; a `settings.json` that is gone gets the backup back; a backup that is gone or unreadable is named in a `WARN`. Then it deletes the kit's files and restores each backed-up file whose installed copy was not edited (an edited one is kept, and `--force` deletes it after a backup and restores the original); a restore it cannot do is a `WARN`. Last, it prints a `left: <path> (<why>)` line for every `.orc-backup-` file it leaves beside a file the kit touched: the kept settings backup, the original of a kept file, a copy of a kit file (`safe to delete`), or one the kit did not make (`it may be the owner's`). An invalid `settings.json` or a tampered `kit` record refuses the uninstall before anything is touched.

`models --tool antigravity --from-stdin [--family <name>]` reads the output of `agy models` on stdin and prints a `models.local.json` fragment. Without `--family`, it picks the first slugs whose name contains `flash` and ends in `-low`, `-medium` or `-high` (so a `flash-lite` slug matches); with `--family <name>`, it picks that family's first `-low`, `-medium` and `-high` slugs (case-sensitive whole segment; ignores suffixes such as `-xhigh` and slugs without a tier suffix). If any tier is missing, it exits 1 and names the missing tiers and the family. A family listed in more than one generation is named with its version, for example `--family 4-neon`: when the three slugs it picks come from different models, it exits 1 and names them.

`build`, `install`, `sync` and `status` take `--profile <name>` (repeatable or comma-separated) to append `profiles/<name>.md` after the tool notes; `check` rejects `--profile`, and the goldens use no profile. The rulebook core is the compact, generic `core/AGENTS.md`; `dotnet-azure-devops` is too large for Antigravity's 24,000-byte cap (the build fails with the size message), so use it with uncapped tools or as a project-level rules file.

## Shared state (~/.orc)

`~/.orc/` (or the folder `ORC_DATA_DIR` names) holds this machine's orc state, shared by every tool: `config.json`, `models.json`, and the `queue/<owner>/<repo>/` state folders. Both config files are optional and orc never creates them or the folder (only `queue run --apply` creates its own state folder); with neither present every command behaves as without them. `install`, `sync`, `status`, `dispatch`, `doctor` and `queue` read both files, and `bench run` reads `config.json` for `binaries` only (never `models.json`); `build`, `check` and `golden` never read `~/.orc`, so their output depends on the checkout alone.

**`config.json`.** Only `version` is required. `~/.orc` is shared by every checkout on the machine, so an entry this checkout does not know is skipped, not fatal: an unknown top-level key, an unknown tool id (in `activeTools`, a `binaries` key, `fallback` or a `routing` value) and an unknown role name (a `routing` key) each print one `WARN <file>: ... (ignored; this checkout does not know it)` line on stderr and are left out of the loaded config. An unknown tool in a `routing` list is removed from that list, and a list left with no known tool drops the role's entry (the warning says so); the same holds for `activeTools`. Anything else wrong (a wrong type or shape, a wrong `version`, invalid JSON, a tool named twice, an empty list) is an error that names the file and every problem (never a value), and the command exits 1. The exceptions are `dispatch --tool`, `bench run` and `queue run` (which use only `binaries`) and a single-tool `install` or `status` that does not fall back to `config.json`'s board (`--board`, a board or `--no-board` recorded in the manifest, or `--sprint-kit`): an invalid file is one `WARN` and the run goes on without it. Routed `dispatch`, `--prefer`, `--all`, `sync`, `doctor`, and a single-tool `install` or `status` that would fall back to `config.json`'s board keep failing on it.

| Key | Value |
|---|---|
| `version` | `1` |
| `activeTools` | The tools this machine uses, in order: what `sync`, `install --all`, `status --all` and `doctor` work through |
| `setupCheckout` | The Orc-istration checkout's path (`doctor` checks that it holds `tools/orc.mjs`; when `--home` is omitted and another checkout runs `install`, `uninstall` or `sync`, a dry run prints a `WARN` and `--apply` refuses unless `--force` is passed; `hooks` prints the same `WARN`) |
| `board` | `{ "url": <board address>, "repo": <Orc-Dashboard checkout> }`; `repo` is needed for a local address, not for an artifact one (an absolute path, `~` is not expanded; suggested clone location: `.orc/board` under your home folder). It is the board default for `install`, `status` and `sync` (one tool or all) when neither flags nor the manifest set or clear one (flag, then manifest, then recorded `--no-board`, then config). `install --apply` saves that board in each tool's manifest, so a later change to `board` here has no effect on an installed tool until you pass `--board`/`--board-repo` or `--no-board`. An artifact `url` here applies to `claude-code` only: every other tool gets no Board line and one notice saying so (passing an artifact `--board` flag to another tool is still refused). `board.local.md` is retired: put its address in `board.url` (with `board.repo` for a local board), delete any unrecorded hand-copied `~/.claude/tools/board-reminder.*` if `doctor` flags it and run `install --tool claude-code --apply` (or `sync --apply`), then delete `~/.claude/board.local.md` (when `board.local.md` and `config.json` name different boards, Claude Code follows `config.json` from then on) |
| `binaries` | Tool id to the executable's absolute path, used by `dispatch`, `doctor`, `bench` and `queue` when `ORC_TOOL_BIN_<TOOL>` is not set (before PATH). A `.js`/`.mjs` path runs under this Node; a `.cmd`/`.bat` shim is refused; a path that does not exist counts as missing, named with the config file |
| `fallback` | The tool tried after a role's own routing entry |
| `routing` | Role name to a tool id or a list of tool ids: a fallback chain tried in order by `dispatch` without `--tool` (the first available tool runs; a list never runs both) |

```json
{
  "version": 1,
  "activeTools": ["claude-code", "antigravity", "codex"],
  "setupCheckout": "C:/Users/<you>/Orc-istration",
  "board": { "url": "http://localhost:8377", "repo": "C:/Users/<you>/.orc/board" },
  "binaries": { "codex": "C:/Users/<you>/AppData/Roaming/npm/node_modules/@openai/codex/node_modules/@openai/codex-win32-x64/vendor/x86_64-pc-windows-msvc/bin/codex.exe" },
  "fallback": "claude-code",
  "routing": { "builder": ["antigravity", "claude-code"], "refuter": ["claude-code", "codex"], "scout": "claude-code" }
}
```

**`models.json`.** The same format as `models.json` in the checkout. The layers are `models.json` (the checkout), then `~/.orc/models.json`, then `models.local.json` (the checkout), each merged two levels deep (tool, then tier) over the one before. `~/.orc/models.json` applies only to `install`, `sync`, `status`, `dispatch`, `doctor` and `queue`; `models.local.json` applies to those and to `build` (`check` validates it; `golden` never reads it). `bench` reads only the checkout's `models.json` (plus `--models`), never `~/.orc/models.json` or `models.local.json`, because a benchmark run must depend on the checkout and the flags alone. A tool id in `~/.orc/models.json` that this checkout does not know is skipped with one `WARN ... (ignored; this checkout does not know it)` line; every other problem there, and any problem in `models.json` or `models.local.json`, is an error. Errors name the file by its full path.

**Routing and fallback.** `dispatch` without `--tool` tries the role's `routing` entry in order, then `fallback`, each tool once. A tool is unavailable when its adapter has no headless recipe, it has no model for the role's tier, or its executable does not resolve (a `binaries` path or a path-shaped `ORC_TOOL_BIN_<TOOL>` that does not exist or is not a regular file, a `.cmd`/`.bat` shim in either, nothing on PATH). The first available tool runs; for each one skipped, stderr gets `dispatch: <tool> unavailable (<reason>); falling back to <next>`. With none available it exits 1 listing each tool and its reason, and starts nothing, `--dry-run` included. With no config, or no entry and no `fallback`, it exits 1 saying it needs `--tool` or a routing entry in the config file. The choice is made before anything starts: a tool that starts and exits non-zero is never retried on another, since a builder may already have edited files. `--tool` is explicit: that tool only, no fallback, and it exits non-zero when that tool cannot run. In both cases below `--dry-run` prints a `note:` line saying why the tool cannot run. A `binaries` entry that does not resolve then exits 1 on a real run, naming it, before anything starts; an `ORC_TOOL_BIN_<TOOL>` that names a missing path or a shim is still tried, and the failure names the override.

**`--prefer <tool>`** puts that tool at the front of the role's chain and keeps the routing entry and `fallback` behind it, each tool once; with no config the chain is that tool alone. It cannot be combined with `--tool`. A `routing` list is a fallback chain, not "run both": for two reviewers on two tools, dispatch twice, once on the routed tool and once with `--prefer <other tool>`, for example `dispatch --role refuter --brief b.md` (Claude Code, as routed) and `dispatch --role refuter --brief b.md --prefer codex` (Codex, falling back to the chain when Codex is unavailable).

**`--model <slug>`** (dispatch; `queue` takes its own `--model`, and every other command refuses it) passes that model to the tool instead of the tier's; the effort is unchanged. It belongs to the first tool in the chain (the `--prefer` tool when given): on a fallback it is dropped, and stderr says so.

**`doctor [--home <dir>] [--json]`** checks, without writing or creating anything, one line each as `OK|WARN|FAIL <check>: <detail>`: `config.json` (absent: WARN with its path; invalid: FAIL; each entry this checkout does not know: one `WARN config` line), `~/.orc/models.json` (absent: OK `none`; invalid: FAIL; an unknown tool id: `WARN models`), `setupCheckout`, and per active tool: whether it has a headless recipe (none: WARN, and no binary, version or sign-in check follows) and, for a tool with one, a model for low, mid and high (WARN naming a missing tier; when `~/.orc/models.json` cannot be read, WARN saying so), the binary and where it came from (env, config or PATH; missing: FAIL; a `.cmd`/`.bat` shim named in `binaries` or `ORC_TOOL_BIN_<TOOL>`: FAIL; only a shim on PATH: WARN naming it and the `binaries` fix), `<binary> --version` within 5 seconds (WARN otherwise; no model run starts), sign-in through the adapter's status command (`claude auth status`, `codex login status`; exit 0: OK `signed in`, otherwise WARN with the exit code; killed after 5 seconds; its output is never printed; Antigravity has none: OK `not checked`), and, for every active tool, the install state in `--home` (default your home) from the comparison `status` makes (clean; drift and not installed are WARN; a corrupt manifest is FAIL, since install refuses it). Then the routing table, one line per role with its chain and the tool that would run (FAIL when a routed role has none, or when `~/.orc/models.json` cannot be read), the board: configured or not, a local address with no `board.repo` (FAIL, as `--all` refuses it), and for an `http://localhost` or `http://127.0.0.1` address one GET of `/api/health` with a 3-second timeout and no redirect following (unreachable, a 3xx redirect, or a non-2xx answer: WARN; other addresses are not fetched), and `WARN` checks whenever retired `<home>/.claude/board.local.md` still exists or an unrecorded hand-copied `<home>/.claude/tools/board-reminder.{ps1,mjs}` differs from this checkout. A check that throws becomes that check's WARN and the other checks still print. It prints paths, tool ids and the board address, never another config value. It exits 1 when any check is FAIL. `--json` prints only `{ "ok": <bool>, "checks": [{ "level", "check", "detail", "tool"? }] }`.

**`sync`, `install --all` and `status --all`** run the command for every tool in `activeTools`, in order, each after a `== <tool> ==` header, with the same other options. `sync [--home <dir>] [--apply] [--force] [--profile <name>|--no-profile] [--board <address> --board-repo <dir>|--no-board]` is `install --all` under a shorter name (dry run without `--apply`; writes nothing into this checkout; rejects `--tool`, `--all` and `--sprint-kit`; exits 1 naming the config file and how to install one tool when `config.json` or `activeTools` is absent). `--all` with `--tool` is an error, and so is `--all` with no config or no `activeTools` (the message names the config file). Every refusal is checked for every tool before anything is written: an artifact `--board` flag is Claude Code only (whereas an artifact `board.url` in `config.json` applies to `claude-code` only and skips other tools with one notice), and `install --all --apply` (and `sync --apply`) first dry-runs every tool, so an unsafe path, a hand-written file in the way or a bad manifest for one tool stops them all (a dry run that exits non-zero with only `WARN` lines counts too, as `dry run exited <code>`). After that, one tool's failure does not stop the rest; the exit code is the worst one, and the last stderr line, `<command> --all: failed for <tool> (exit <code>), ...`, names every tool that did not exit 0.

## Method tooling

These commands check or do the manual steps the rulebook asks for. None of them writes to the board.

- `brief new [--role <name>] [--out <file>]` (with `--out`, as for `costlog`, an existing file is refused unless `--force` is given) prints the marching-orders template, parsed from the numbered list under "Marching orders" in `core/AGENTS.md` (items 9 to 11 only for builder, refuter and debugger; item 9, Intent, is prefilled `n/a` for a builder or debugger). `brief lint <file> [--role <name>]` checks a brief: every item present, in order and filled in; nothing but an optional title heading before item 1 and nothing but the `BOARD:` line after the items' own (indented or fenced) lines; item 4 names a command (a code span, a fence, or a line starting with a runner word such as `npm` or `node` and an argument); item 6 states a cap; for `--role refuter`, item 9 (Intent) is a path, the criteria or `none: <why>`, never empty, `n/a`, a placeholder such as `TBD`, or a `none` without the colon form; a brief still on the old numbering is told that Intent is new at item 9; `BOARD: none` is accepted; a `BOARD:` line has the form `BOARD: <address> card cards/<id> stage <label>` (Claude Code's `slug <uuid>` after the address is accepted). It exits 1 with one line per problem.
- `review-tier [--base <ref>] [--repo-dir <dir>]` reads `git diff --name-only --no-renames <base>...HEAD` (default base `origin/main`) and prints `Light-eligible` when every path is a test (`tests/`, `test/`, `__tests__/`, `spec/`, `*.test.*`, `*.spec.*`, `*_test.*`) or a doc (`*.md`, `docs/`), else `Full` with the first three deciding paths. Light still needs a refuter ACCEPT after mutation checks (conditions 2 and 3 of "Pre-PR review tiers"). Prompts count as product, not docs: `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `SKILL.md`, `*.agent.md`, `core/`, `roles/`, `agents/`, `commands/`, `profiles/`, `.claude/`, `.agents/`, `.codex/`, `.cursor/`, `.gemini/`, `adapters/*.notes.md`, `adapters/<tool>/`, `standards/`, `review/`, `workflows/`, `orchestration/standards.md` and `orchestration/sprint.md` make it `Full`; uncommitted changes print a warning, since they are not in `<base>...HEAD`.
- `costlog --session <id> (--board-export <file> | --board <http://localhost:port> --board-repo <dir>) [--out <file>]` drafts a cost log in the "Record format" of `orchestration/README.md`: one row per `<agent> dispatched on #<task>` event, ended by the next top-level event naming the same card (its text is the Result). Card `tokens` go in a per-card table, because the board records tokens per card, not per dispatch. Model, tools, value, project, orchestrator context, loop signal and spec misses are `TODO`. `--board` reads through `node <board-repo>/local/board.js export`.
- `dispatch [--tool <id> | --prefer <id>] --role <name> --brief <file> [--model <slug>] [--dry-run] [--timeout <seconds>] [--no-lint]` runs one role headlessly at its tier, on `--tool` or on the tool `~/.orc/config.json` routes the role to (routing, fallback, `--prefer` and `--model`: [Shared state](#shared-state-orc)): Antigravity as `agy -p <brief> --agent <role> --model <models.json headless slug> --output-format json --disable-slash-commands [--effort <effort>]` (checked against agy 1.5.16: agy reads stdin only in stream-json mode, so the brief is one argument, and `--disable-slash-commands` keeps a brief starting with `/` from running as a slash command or skill; the generated roles are main agents, `mainAgent: true`, so `--agent` can select them), Claude Code as `claude -p --agent <role> --model <tier model>` with the brief on stdin, Codex as `codex exec --model <tier model> --sandbox <read-only|workspace-write> [-c model_reasoning_effort="<effort>"] [-c windows.sandbox=mxc] -` with the role body, a `---` line and the brief on stdin (`read-only` only for `scout` and `researcher`, which must report inline, because Codex's read-only sandbox blocks every write, a scratch file included; `workspace-write` for every other role, since the refuter runs tests and builds a throwaway worktree and the `review-*` roles write at most an overflow scratch report, so their no-edit rule rests on the role body; on Windows, orc adds `-c windows.sandbox=mxc` before `-` for every role to select the MXC sandbox, because without a sandbox selection Codex blocks process launches there — see [`example-prompts.md`](example-prompts.md#native-windows-execution-checks); a headless Codex run has no web tool, and its network access depends on your Codex sandbox configuration; the effort only when the tier or role has one; `codex exec` refuses to run outside a git repository, and with an npm install `ORC_TOOL_BIN_CODEX` or `binaries.codex` must name the real `codex.exe`, not the `codex.cmd` shim). Other tools exit 1 with "no headless recipe". The brief is linted first, is never put through a shell, `--dry-run` prints the command and exits 0, a real run streams the tool's output and exits with its code, and `--timeout` (whole seconds, 1 to 86,400) kills the process tree (exit 124; on Windows through `taskkill /T /F`, killing the child itself when `taskkill` fails, with a stderr line saying its child processes may still run); Ctrl-C or a kill of orc kills the tree too (exit 130 or 143). The brief is read once, BOM-stripped and UTF-16 decoded, and that text goes to the tool. `ORC_TOOL_BIN_<TOOL>` (e.g. `ORC_TOOL_BIN_CLAUDE_CODE`), then `binaries` in `~/.orc/config.json`, then PATH, give the executable; a Windows `.cmd` shim is not started. A brief passed as an argument is refused (nothing started) when it holds a NUL byte or the command line would pass about 32,000 bytes; a tool that is not installed is named with its override variable.
- `hooks --home <dir> [--apply] [--node]` merges only the `hooks` block (never `permissions` or other keys) of `adapters/claude-code/settings.example.json` (or, with `--node`, of `adapters/claude-code/hooks.node.example.json`: the board reminder as `node <home>/.claude/tools/board-reminder.mjs` and the git guard as `node <home>/.claude/tools/guard.mjs`, no PowerShell) into `<home>/.claude/settings.json`, creating it when absent. `<you>` and `<home>` paths become the real home, and `<setup>` becomes the checkout running `orc.mjs` (for the worklog and peon hooks under `extras/`). Run `hooks` from the checkout you keep, because the worklog and peon hook commands point into it. A hook is added only when no hook under that event and matcher runs the identical command; the same command under a different matcher is added beside it, with a note naming the existing matcher; an existing entry under the same event (whatever matcher it sits under) that still points at `.claude/tools/worklog/` or `.claude/tools/peon/` is reported as a stale entry to replace (naming the matcher it was found under and the new path) and is not duplicated; existing keys and hooks are never removed, reordered or rewritten. It is a dry run without `--apply`; `--apply` backs the file up first (only once the new content could be written), keeps a UTF-8 BOM, and refuses a file whose top level is not a JSON object. For each hook it adds whose script (the quoted `.ps1` or `.mjs` path in the command) is not on disk, it prints `WARN hook script not found: <path>` on stderr. `--home` has no default.
- `calibration [--logs <dir>] [--min-precision <0..1>] [--out <file>] [--force]` reads the review panel's run logs (default `<repo top>/.orc/reviews`, from the current folder) and prints per-lane precision from their developer verdicts (a verdict carrying `(agent)` anywhere in its cell is counted apart, outside precision and the triaged count), escaped defects from each log's `## Escaped defects` table, and recall, `confirmed / (confirmed + escaped)`, shown once a lane has at least one escape and 5 or more such rows (otherwise `n/a`); lanes under `--min-precision`, with 3 or more false positives or with 2 or more escapes are flagged. Other tables in a log (Runtime checks) are ignored. A `Leads:` or `Verification:` line missing a count, an escaped-defects row it cannot read (a `#` that is not a number, too few cells, a table whose header is not the documented one) and an `## Escaped defects` section with no rows are listed under **Parser warnings**, with the number of rows dropped and why, so an unreadable table never reads as zero escapes. Format and procedure: `review/calibration.md`.
- `corpus list` prints each regression-corpus case in `tests/fixtures/corpus/` of the checkout (`--repo`) with its lanes and title, and a `WARN` line on stderr for a case with no title or no `Lanes:` line and for a folder with `expected.md` but no `case.md`; `corpus score --case <id> --report <file>` scores a panel report (the `review/PROCEDURE.md` Step 4 format) against the case's `expected.md`: an expected row is found when a finding under Must fix, Review before submitting or Suggestions names the same file with its first line in one of the row's ranges (Lines takes `a-b`, one line, or a comma list; the lane is shown, not required; bullets may start `-` or `*`, unindented). It prints `FOUND`, `MISSED` and `EXTRA` lines and exits 1 when anything expected is missed. Format and procedure: `review/corpus.md`.
- `bench list | bench run [--case <id>]... [--variant <label>] [--models <file>] [--tool claude-code] [--out <dir>] [--budget-usd <n>] [--timeout <seconds>] [--runs <n>] [--keep] [--keep-output] [--dry-run] | bench report [--dir <dir>] [--out <file>] [--force]` is the replay benchmark (Claude Code only). `list` prints each case in `tests/fixtures/bench/` of the checkout (`--repo`) with its kind and title, and a `WARN` line on stderr for each problem in a case. `run` gives each case (default all) a scratch repo in a temp folder (branch `base`; for a refute case the change committed on `change`), runs the checkout's `builder` or `refuter` there as `claude -p --agent <role> --agents <the role's generated definition as JSON> --model --effort --output-format json --permission-mode acceptEdits --allowedTools <list> --max-budget-usd <n> --no-session-persistence` with the brief on stdin and no shell, scores it (a build case by its hidden acceptance command, a refute case by its `VERDICT:` line and the planted defects it cites), and writes one JSON result per run to `<out>/<UTC stamp>-<variant>/` (default `<repo top>/.orc/bench`). Model and effort come from `models.json` merged with `--models <file>` (the `models.local.json` shape); neither `~/.orc/models.json` nor `models.local.json` is read, because a benchmark run must depend on the checkout and the flags alone. `ORC_TOOL_BIN_CLAUDE_CODE`, then `binaries.claude-code` in `~/.orc/config.json`, then PATH give the executable (an invalid `config.json` prints one `WARN` and the run goes on without `binaries`). Defaults: variant `baseline`, budget 2 USD per run, timeout 900 seconds, 1 run. A non-zero exit, timeout, budget stop or unparseable output is a result with `outcome: "error"`, and the command exits 1 when any run errored; `--dry-run` prints each command and starts nothing; any `--tool` but `claude-code` exits 1. `report` prints, per variant, runs, errors, build pass rate, verdict accuracy, the false-ACCEPT and false-REWORK rates, planted defects found, tokens, cost, and tokens and cost per pass, then a per-case table; a rate over fewer than 5 runs shows its count. Format, scoring and the result schema: `orchestration/bench.md`.
- `queue list | queue run [--repo-dir <dir>] [--label <l>] [--author <login>]... [--base <branch>] [--max <n>] [--until <HH:mm>] [--budget-usd <n>] [--timeout <seconds>] [--model <m>] [--allow <tool rule>]... [--state <dir>] [--issue <n>] [--apply]` is the unattended issue queue (Claude Code only). `list` prints each open issue with the label (default `orc-queue`) in the `--repo-dir` repo (default the current folder's; its `origin` must be on GitHub) as `eligible` or `skipped:` with the reason: author not allowed (default: only the logged-in `gh` user; `--author` repeats), a marker in the state folder, a `queue/issue-<n>` branch on `origin`, an open PR with that head, or a local `queue/issue-<n>` with no marker (never deleted, unless the queue left a `leftover-<n>.json` note for it). Only the number, title, body and author are read; comments never are. `run` is a dry run without `--apply` (`--dry-run` is refused): it prints the eligible issues oldest first, the worktree, the branch names and the `claude` command, and changes nothing. With `--apply`, per issue (up to `--max`, default 1; none started at or after the `--until` deadline, the next HH:mm at or after the run's start, or nothing at all when the run starts less than an hour after HH:mm), it checks out `<state>/wt` (re-added when broken or owned by another clone) detached at `origin/<base>` (default the repo's default branch) with `--force` and `git clean -ffdx`, switches to `queue/issue-<n>`, runs `claude -p --output-format json --permission-mode acceptEdits --max-budget-usd <n> --no-session-persistence --strict-mcp-config --model <m> [--effort <e>] --allowedTools <list> --disallowedTools <deny list>` there with the prompt on stdin, no shell, and an environment that closes the plain git push routes (defaults: 5 USD, 3600 seconds, the Claude Code high tier from `models.json` with `~/.orc/models.json` and `models.local.json` over it), and classifies the result: a usage limit writes no marker and stops the run with exit 0; `done` with a commit, HEAD still on the branch and a clean tree makes the script push `queue/issue-<n>` (never forced, with its own git hooks off) and run `gh pr create --draft` (body `Refs #<n>`, the Orc-istration footer last), marker `handled` (a provisional `failed` marker recording the push is written before the PR opens); `blocked` or no commit pushes nothing, marker `blocked`; a session that changed the repository's git configuration (`.git/config`, `.git/info/attributes`, the worktree's `config.worktree`) is restored and ends `failed` with nothing pushed; a run-level failure (`claude` cannot start, API error 401, 403 or 5xx, an authentication failure, a worktree that cannot be prepared) is `aborted`: no marker, the run stops, exit 1; Ctrl-C stops the run with no marker either; anything else is marker `failed` and exit 1. The script's own git and gh calls time out (300 s; fetch, `ls-remote` and push 600 s). `--allow` adds one tool name or one `Bash(<command>)` rule and refuses push, `gh`, shells and command runners (also `npm exec`, `pnpm dlx` and the like), shell operators, quotes, an environment prefix, git subcommands outside a short list, and denied tools; the user's own settings `allow` rules also apply, and the deny list beats them. `--issue <n>` reruns one issue despite a `failed` marker, or, when its branch was pushed and only `gh pr create` failed, opens the draft PR alone (title and body rebuilt by the script), or, when the push failed, pushes the kept commit and opens the PR; it refuses, saying to delete the marker, when the recorded commit is gone. `run` prints a `WARN` when the base branch is not protected on GitHub, when admins can bypass its protection, or when that cannot be checked (classic protection only: rulesets are not read, and whether a pull request is required is not checked). The session is not a sandbox (it runs code as the user); the backstops are the author allow-list, base-branch protection and review of every draft PR. The state folder (default `~/.orc/queue/<owner>/<repo>/`, or `$ORC_DATA_DIR/queue/<owner>/<repo>/`) holds the markers, `queue.log`, `run-<n>-<stamp>.json`, `leftover-<n>.json` notes, the lock and the worktree. It refuses (exit 1, nothing changed) a folder that is not a git repo with a GitHub `origin`, a missing or logged-out `gh`, a `--base` not on `origin`, and a `--budget-usd`, `--max` or `--timeout` that is not a positive number. `ORC_TOOL_BIN_CLAUDE_CODE`, then `binaries.claude-code` in `~/.orc/config.json`, then PATH point at `claude` (an invalid `config.json` prints one `WARN` and the run goes on without `binaries`); `ORC_TOOL_BIN_GH` and `ORC_TOOL_BIN_GIT` override `gh` and `git`. Procedure, guard rails and scheduling: `orchestration/queue.md`.
- `metrics capture --workflow <name> [--session <id> | --transcript <path>] [--log <run log>] [--mode lite|full] [--version <v>] [--out <dir>] [--print]` writes one run's token, context and outcome metrics from a Claude Code transcript (default `<repo top>/.orc/metrics/`); `metrics report [--dir <dir>] [--prices <file>] [--out <file>] [--force]` aggregates them. Format: `review/metrics.md`. Neither reads `--repo`.
- `check` builds every adapter from `models.json` only (never reading `~/.orc`), enforces adapter caps and tool allowlists, compares every tool's build with `tests/golden/<tool>/` (any missing, differing — with its first differing line — or stale golden file, or any `tests/golden/<id>/` folder no adapter owns, is a `FAIL` naming the source to edit and `run node tools/orc.mjs golden`), validates `models.json` and `models.local.json` (tool ids must be adapters, tiers `low`, `mid`, `high`, plus `headless` slugs per tier, values strings, and `effort` one of `low`, `medium`, `high`, `xhigh`, `max`, `ultra`), and validates every archive entry in `standards/` (except `README.md`): `id` equals the file name, `kind` is `language`, `framework` or `tool`, `detect` is a non-empty list, every `requires` id exists, `reviewed` is `YYYY-MM-DD`, `sources` is non-empty and every `[n]` in the body (outside code) is within range, and the body has a `## Review checklist` section with at least one `- [ ]` item.

CI (`.github/workflows/test.yml`) runs `npm test` and `check` on Ubuntu and Windows, and the worklog self-test on Windows.

## Repo standards

`standards` reads the archive in this checkout's `standards/` (format in `standards/README.md`). For this command `--repo <dir>` names the project, not the Orc-istration checkout. `--stack`, `--from` and `--json` are refused by every other command. Within `standards`, `list` and `show` take no option but `--repo`; `detect` refuses `--stack`, `--from`, `--out`, `--force` and `--apply`; `apply` refuses `--json`. The setup procedure that uses it is `orchestration/standards.md`.

- `standards list` prints one line per archive entry: `<id>  <kind>  <title>  (reviewed <date>)`.
- `standards show <id>` prints the archive file. An unknown id exits 1 and lists the known ids.
- `standards detect [--repo <dir>] [--json]` (default: the current folder) walks the project without following symlinks or junctions, skips folders named `.git`, `node_modules`, `bin`, `obj`, `dist`, `build`, `vendor`, `target`, `.venv`, `venv`, `__pycache__` and `.claude`, and stops after 50,000 entries with a warning. A folder it cannot read is skipped and counted, with `WARN could not read N folder(s); results are partial` on stderr; an unreadable project root exits 1. It matches each entry's `detect` globs (`*` and `?`, case-insensitive) against file base names and prints, per detected id, the match count and up to 3 example paths, most matches first; ids pulled in only through `requires` (transitively) show `required by <id>`. `--json` prints `{repo, standardsFile, current, detected: [{id, title, kind, matches, examples, requiredBy}], archive, truncated, unreadable}`, where `standardsFile` says whether `STANDARDS.md` exists and `current` is `{stacks, imports}` parsed from its orc marker, or `null` when it has no valid marker. It exits 0 even when nothing is detected.
- `standards apply --repo <dir> (--stack <ids> | --from <path>)... [--out <rel>] [--apply] [--force]` composes the project's standards file:
  - `--stack` takes archive ids (repeatable or comma-separated) and adds their `requires`, saying so. `--from` (repeatable) takes a `.md` file, or a folder whose `.md` files are taken non-recursively, sorted by name; a folder leaves out the target, and a `--from` that is the target (same real path) exits 1. A `--from` file whose frontmatter has a top-level `sources:` key is an archive-format entry: it must parse (`#` comment lines are ignored), its `sources` must be a non-empty list and it must have an `id`, or it exits 1 with `--from <path>: <file name>: <parse error | sources must be a non-empty list | an archive-format entry needs an id>`; it is then validated with `check`'s per-entry rules (except that `requires` ids need not exist), and an invalid one exits 1 with its problems. Frontmatter without `sources:` (such as `id:` and `title:` only) is a plain import. The marker records imports by file name, so one file reached twice (repeated, a folder plus a file in it, or the same file in another case on Windows) exits 1 with `passed twice: <path>`, and two different files with the same file name ignoring case (two folders each with `style.md`), or a file name containing `,`, `;` or `-->`, exit 1 naming the files. `--out` defaults to `STANDARDS.md` and must be relative, stay inside the project, have no `.git` segment, and not pass through an existing file. Builders, refuters and `detect` read the root `STANDARDS.md`, so a non-default `--out` is for review or staging.
  - Sections: languages, then frameworks, then tools (each by id), then archive-format imports, then the other imports, each group in the order given. Each stack section is the archive body with every heading demoted one level, a `Sources` list numbered to match its `[n]` citations, and a `Reviewed <date>` line. An archive-format import is rendered like a stack section and recorded in the marker's `imports` by file name. Each other import is `## Imported: <file name>` and the file's body, with any leading YAML frontmatter removed and headings demoted outside fenced code. A leading `---` ... `---` pair is frontmatter when it has a top-level `key:` line and every other non-blank line is a `#` comment, an indented line, or a top-level `- ` item under a key; otherwise (a heading over a list, say) it is a pair of horizontal rules and is kept. A pair around a lone `Note: x` line is valid YAML, so it is stripped.
  - Line 1 is `<!-- orc standards: stacks=<ids>; imports=<names>; sha256=<hex> -->`; the hash covers the rest of the file (LF line endings), so a later run can tell an untouched file from an edited one.
  - Without `--apply` it is a dry run: it prints the target, its state and the section list, and writes nothing. States: `create` (absent), `unchanged` (identical), `replace` (marker present, hash matches, nothing dropped), `REPLACE DROPS` (hash matches, but the new composition leaves out a stack id or import name the marker records; the refusal names them), `REPLACE EDITED` (hash does not match) and `REPLACE HAND-WRITTEN` (no marker). With `--apply`, the last three are refused with exit 1 unless `--force` is given, which first copies the file to `<file>.orc-backup-<stamp>`. As with `install`, the dry run still exits 0 for them and adds an `--apply would refuse` line.
  - It refuses a target whose path, or any folder below the project, is a symlink or junction, or whose real path leaves the project. An unknown stack, a missing `--from` path, or neither `--stack` nor `--from` exits 1. It writes only the `--out` file (through a temp file in the same folder, renamed over the target), as UTF-8 with LF line endings, and never fetches anything: save a URL as Markdown first and pass it with `--from`.
